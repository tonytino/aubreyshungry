- `[manual]` Planning weeks now run Sunday→Saturday and are identified by the date of their starting Sunday (issue #23, ADR-008): `content/weeks/<YYYY-MM-DD>.json` with a `weekStart` field validated by `WeekStartSchema` (replacing `isoWeek` / `IsoWeekSchema`), `DAYS` reordered Sunday-first, `app/utils/iso-week.ts` renamed to `app/utils/week-dates.ts` (`weekStartDate()`, `formatWeekRange()`, `weekLabel()`), and `scripts/plan-reminder/current-iso-week.mjs` renamed to `scripts/plan-reminder/current-week.mjs` (prints `YYYY-MM-DD`). "Today" resolves in `America/Denver` in both the generation skill and the reminder workflow. Breaking for any instance holding week content: there is no automatic migration path from `YYYY-Www` identifiers — rename week files to their starting Sunday's date and rename the field before upgrading.
- `[manual]` `/generate-week` takes no week argument any more (ADR-008 amends ADR-007): it reads the latest `weekStart` on disk and asks the owner whether to regenerate that week or generate the next one, offering the current Mountain-Time week and the one after it when no weeks exist yet. The mandatory `plan-<isoweek>` branch is gone — the session works on the branch it is already on — and the plan PR title is now `feat(plan): week of <weekStart>`.
- `[propagate]` The Thursday plan-reminder workflow now checks the **upcoming** week (`currentWeekStart() + 7 days`) instead of the current one, so the before-weekend nudge names the week you are about to shop for — the same Sunday the `/generate-week` prompt offers as "generate the next week".
